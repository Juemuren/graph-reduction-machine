# 网站实施方案

## 目标与阶段

站点按四个阶段建设。每个阶段完成后单独验收，再决定下一阶段的具体范围。

| 阶段 | 交付内容 | 运行位置 |
| --- | --- | --- |
| 第一版：可阅读 Examples + Documents + Codes | 示例说明、源码、现有比较图表和数据的静态页面 | 站点构建时生成页面 |
| 第二版：可交互 Playground | 编辑、编译、归约和解码源码 | 优先验证浏览器中的 Haskell WebAssembly |
| 第三版：可使用 LSP | 在 Playground 中提供 λ 和 SKI 图的语言服务 | 浏览器中的语言分析与编辑器集成 |
| 第四版：可运行 Benchmark | 在网页中运行 `compare_*.py` 对应的测量流程 | 待第二版的验证结果确定 |

## 第一版：可阅读 Examples + Documents + Codes

第一版不要求用户在网页中执行源码。现有的比较结果仍由仓库中的脚本生成，站点负责展示。

### 内容来源

- `examples/*/README.md` 是各示例的说明正文，包括公式、代码链接和已有图片；同目录的 `.lambda` 和 `.ski` 文件是源码的唯一维护位置，站点在构建时读取它们，生成带语法高亮、行号和复制按钮的只读源码页，并提供原文件下载；同目录的 `.png`、`.csv` 是已经生成的比较结果，页面展示图片，并提供 CSV 下载。`compare.json` 可在页面中说明测量方法，但第一版不支持在 Web 里运行比较。
- `docs/syntax.md` / `docs/compiler.md` / `docs/interpreter.md` / `docs/lsp.md` / `docs/architecture.md` / `docs/lib.md` 和 `lib/*.lambda` 作为站点中的参考文档和源代码入口。站点页面链接这些文档时，要有可用的站内目标。

站点不复制示例正文和源码到另一套手工维护的内容目录。若构建工具无法直接读取仓库外层的 Markdown，可以在构建时生成临时内容，生成物不提交。源码和结果文件保留原路径；页面路由由文件路径确定，以免以后增加示例时逐项配置。

### 页面结构

| 页面 | 内容 |
| --- | --- |
| 首页 | 项目目标、从 λ 到 SKI 图再到结果的流程，以及示例和文档入口 |
| 示例索引 `/examples/` | 按现有目录列出 λ、SKI、编码、斐波那契、圆周率、自然常数、符号微积分 |
| 示例详情 `/examples/<目录>/` | 渲染 README，嵌入源码入口和现有图表；保留公式、表格与原有叙述 |
| 源码页 `/examples/<目录>/<文件名>/` | 只读源码、复制、下载、返回示例说明 |
| 文档页 `/docs/<文档名>/` | 语法、架构、编译器、解释器、语言服务器及标准库参考 |
| 标准库页 `/lib/<文件名>` | 标准库实现 |

页面须支持窄屏阅读、键盘访问和清楚的代码块横向滚动。公式使用构建时渲染；普通内容阅读无需浏览器执行 JavaScript。示例和文档中的相对 Markdown 链接要转换为站内路由或静态资源路径，并在构建时检查断链；`docs/compiler.md` 和 `docs/interpreter.md` 引用的 `docs/architecture.md` 应生成站内页。源文件里已使用 `lambda`、`ski` 等代码围栏；若高亮器没有相应语法，先提供易读的纯文本显示，再补自定义语法。

### 技术组织

建议在仓库新增独立的 `site/` 目录，使用 Astro 生成纯静态文件。Astro 的构建时内容集合适合从本地 Markdown 生成页面，静态路由可由 `getStaticPaths()` 创建；`public` 资源会原样复制到输出目录。选用它主要是为了将内容页与第二版的交互组件放在同一站点中。具体依赖版本在实施时锁定。

参考信息:

- [Astro 内容集合](https://docs.astro.build/en/guides/content-collections/)
- [Astro 项目结构](https://docs.astro.build/en/basics/project-structure/)

构建过程建议如下：

1. 扫描 `examples/` 和 `lib/` 的 README、源码、图片和 CSV，生成页面索引和静态资源映射。
2. 渲染 Markdown 与数学公式，并改写相对链接。
3. 生成示例页、源码页和参考文档页。
4. 检查所有预期页面和内部链接；构建产物只包含静态文件，可部署到任意静态文件托管服务。

### 第一版验收条件

- 七个现有示例目录均可从索引访问。
- README 的公式、图片、源码链接正常。
- 源码可复制和下载。
- 已有比较图表和 CSV 可查看或下载。
- 架构文档、标准库源码及纳入站点的文档间链接可访问。
- 站点可在没有编译器和解释器运行时的环境中构建和访问。

## 第二版：可交互 Playground

第二版要求可以在浏览器中运行编译器和解释器。

### 浏览器执行路线

优先做一个独立的 WebAssembly 可行性验证，再实现完整界面。GHC 的 `wasm32-wasi` 交叉编译产物可在浏览器运行，JavaScript FFI 可暴露 Haskell 函数；目前官方仍将该工具链标为技术预览，因此本项目的依赖、生成解析器和最终产物需要实测。

参考信息:

- [GHC WebAssembly 指南](https://ghc.gitlab.haskell.org/ghc/doc/users_guide/wasm.html)

验证顺序：

1. 将编译器、解释器和生成解析器所需的核心模块，与语言服务器及其依赖分开构建；保留现有命令行入口。
2. 用交叉编译工具链构建最小 WASM 入口，验证标准库的构建时嵌入、解析器生成及依赖可用性。
3. 从 JavaScript 传入源码字符串，验证一次 λ 编译、一次 λ 归约、一次 SKI 归约、一次 SKI 解码。λ 编译器需要验证输出，SKI 解释器需要验证返回结果和归约步数。
4. 记录产物体积、首次加载时间、上述操作的耗时及内存使用，再确定完整 Playground 的限制。

现有 [编译器入口](../src/Compiler.hs) 和 [解释器入口](../src/Interpreter.hs) 已提供基于字符串的函数，可作为 Web 接口的核心。现有 [模块加载器](../src/Compiler/ModuleLoader.hs) 读取磁盘文件；浏览器版应把编辑器中的多文件内容和标准库映射为虚拟路径，传给编译函数，而不是依赖本地文件系统。标准库目前在构建时通过 Template Haskell 嵌入，交叉编译时需单独验证。

### 交互范围

Playground 的初始界面包含 λ/SKI 源码编辑区、阶段选择、编码与解码选项、运行按钮、结果/错误区和归约步数。示例页可用“在 Playground 中打开”将源码和相关导入文件预置到编辑器；同一会话中的文件按相对路径解析。运行放在 Web Worker 中，提供归约步数上限和取消/超时处理。λ 阶段的 β/η 归约可能在进入 SKI 解释器之前就消耗大量资源，因此需要单次运行的时间和内存边界。

### 第二版验收条件

- 示例可以一键载入。
- 能完成 `λ -> SKI -> 结果` 的完整流程。
- 错误能定位到当前阶段。
- 文件导入和标准库能工作。
- 页面在长时间计算时仍可操作。

若 WASM 验证无法达到可接受的加载与运行表现，再根据实测结果评估其余执行方案。

## 第三版：可使用 LSP

第三版在第二版的编辑器和虚拟文件基础上加入语言服务。目标是让浏览器中的 λ 和 SKI 图编辑体验覆盖现有语言服务器的主要功能；具体功能见 [语言服务器文档](lsp.md)。

现有 `LanguageServer.Lambda`、`LanguageServer.Ski` 和 `LanguageServer.Common` 包含可按源码和光标位置调用的分析函数。浏览器端优先复用这些分析逻辑，把结果接入编辑器；`LanguageServer.hs` 负责的 LSP 进程协议、文档同步及磁盘读取不直接搬入网页。跨文件的悬停和跳转应从第二版建立的虚拟文件表读取导入模块。先验证所需模块能否与核心编译器一同构建为 WASM，再确定浏览器接口和编辑器适配层。

### 语言服务范围

- 核心 λ：语法和名称诊断、语义高亮、补全、悬停、签名提示、文档符号、跳转到定义、查找引用和重命名。
- SKI 图：语法和节点诊断、节点补全、悬停、文档符号、跳转到定义、查找引用和重命名。
- 多文件能力：导入名称的悬停和跳转使用 Playground 当前会话中的文件；打开或修改文件后更新受影响的诊断和查询结果。

### 第三版验收条件

- λ 和 SKI 图在编辑时能显示诊断，并能使用补全、悬停及导航；范围与现有语言服务器文档对应。
- 重命名和签名提示等现有功能在适用语言中可用，跨文件导入的悬停和跳转可定位到会话中的文件。
- 编辑器与现有命令行语言服务器对相同测试样例给出一致的关键结果；长文件或频繁输入时页面保持可操作。

## 第四版：可运行 Benchmark

现有 `scripts/compare_index.py`、`compare_binary.py`、`compare_real.py` 及 `compare_common.py` 包含三类内容：

| 部分 | Web 侧处理方式 |
| --- | --- |
| `examples/*/compare.json` 的方法、输入范围、编码/解码和步数上限 | 继续作为比较配置的数据来源 |
| 生成入口表达式、逐点测量、检查同一输入的结果是否一致 | 按现有语义在 Web 侧实现，并与 Python 结果核对 |
| `subprocess` 调用、磁盘读写、Matplotlib 绘图 | 分别改为调用 Playground 运行接口、浏览器下载、Web 图表 |

第四版先评估少量输入的交互式比较，再决定是否开放网格或高步数测量。图表至少应保留方法、输入、步数、解码值和达到上限的状态；实数比较还需保留精确值、误差计算和精度规则。浏览器中的大批量测量需要限制范围并允许取消。已有静态 CSV/PNG 始终作为可阅读的基线结果；动态结果要标明运行环境和参数，避免将不同浏览器的耗时误作可直接比较的性能指标。归约步数可用于比较算法，但它与墙钟时间是不同指标。

是否实施第四版，依据第二版的加载体积、单次运行性能、批量运行时的内存占用，以及用户是否需要修改比较配置来决定。
